# SEO-статьи и автописатель — дизайн

Дата: 2026-09-30. Образец: «Грани» (ветка `feat/seo-autopilot`, коммит `4b7caf0`, `docs/seo-article-writer.md`).

## Решения владелицы

- Статьи публикуются автоматически, без ручной вычитки, дважды в неделю (вторник и пятница).
- Автописатель мержит только собственный PR со статьёй и только при зелёных проверках. Любой другой код — только по «да» владелицы.
- Научных источников у темы нет. Вместо проверки по Crossref статья опирается только на вычитанные тексты арканов, клеток Лилы, совместимости и на формулы расчёта из кода. Не выдумываются факты, авторы, даты, «история метода».
- Стоп-лист как у арканов: без предсказаний, диагнозов, «кармы», запугивания. Язык гипотез, обращение «вы», нейтральный род.
- Адрес раздела: существующий `/blog` (вариант А). Четыре готовые статьи остаются компонентами на своих адресах.
- Картинки: только готовые иллюстрации (арканы, клетки Лилы, `hero.webp`), выбираются из фиксированного списка.

## 1. Как устроены статьи на сайте

- Статья — файл `packages/content/articles/<slug>.md` с шапкой (front matter): `title`, `metaTitle`, `description`, `date`, `image`, `cluster`, `faq`, `basis` (ключи «на чём основана»).
- `pnpm content:build` собирает статьи в `packages/content/src/generated/articles.json` (как арканы и клетки). Парсер шапки и тела — в `packages/content/src/articles.ts`.
- `apps/web/src/lib/blog.ts` объединяет ручные записи `BLOG_POSTS` (компоненты) и Markdown-статьи, сортирует по дате. `/blog` и `/blog/[slug]` показывают оба типа; sitemap и `PUBLIC_PATHS` подхватывают адреса автоматически.
- Отображение Markdown — собственный небольшой рендер (`##`, абзацы, списки, `**жирный**`, внутренние ссылки). Прочий синтаксис тест отвергает. Внешняя библиотека не подключается.
- Страница Markdown-статьи: `Article` JSON-LD, `FAQPage` JSON-LD из `faq`, блок «На чём основана статья», дисклеймер сайта.
- Блок «На чём основана»: ключи (`arcana`, `positions`, `matrix-formulas`, `compat-texts`, `lila-cells`, `lila-rules`) отображаются человеческими названиями; тест проверяет, что у каждого ключа есть реальный файл.
- Контент-план — `packages/content/src/content-plan.ts`: тема (`slug`, `title`, `primaryQuery`, `cluster`, `image`, `basis`, `internalLinks`, `status: draft | published`). Тема становится `published` ровно тогда, когда выходит статья.

## 2. Защита от ошибок (замена вычитки)

Тесты целостности (`packages/content/src/articles.test.ts`, `content-plan.test.ts`, `apps/web/src/lib/blog.test.ts`); автописатель их не правит.

- Стоп-лист: `STOP_PHRASES` из `check.ts` плюс основа «карм», запугивающие обороты; «предсказание» допустимо только в отрицании.
- Тон: только «вы» (без «ты/тебе/твой», кроме названия «Твой оракул»); тест ловит очевидные формы рода («вы были рады», «вы сделали»), остальное — инструкция автописателя.
- Структура: 4 000–9 000 знаков, ≥3 раздела `##`, первый абзац без «в этой статье», `description` 90–175 знаков, `metaTitle` ≤75, дата не в будущем, уникальный slug.
- Ссылки: все внутренние ссылки ведут на адреса из `PUBLIC_PATHS`; минимум одна на калькулятор/Лилу/совместимость и минимум одна на страницу аркана или клетки, если тема их касается; внешних ссылок нет.
- Основание: ≥1 ключ `basis`, все ключи существуют.
- Числа и названия: упомянутые номера арканов (1–22), клеток (1–72) и их названия сверяются с реальными текстами.
- План: `published` в плане ⇔ есть файл статьи; картинка существует.

Защита процесса:

- Автописатель работает только в ветке `article/<slug>` и меняет только `packages/content/articles/*.md`, `packages/content/src/content-plan.ts`, `packages/content/src/generated/articles.json`. В `ci.yml` добавляется проверка: для веток `article/*` любые другие изменённые файлы валят проверку.
- Мерж только при зелёном `ci` (typecheck + тесты). После двух неудачных исправлений PR остаётся открытым с комментарием.
- Остановка: открыт незавершённый PR `article/*`, тема оказалась стоп-темой, не хватает наших текстов для темы.
- IndexNow: шаг в `deploy.yml` отправляет в Яндекс адреса изменённых статей; ключ в `apps/web/public/indexnow.txt` (не секретный); сбой даёт предупреждение, деплой не падает.

## 3. Автописатель и расписание

- Инструкция: `docs/oracle-article-writer.md` (по образцу «Граней», без Crossref): обновить master и проверить открытые `article/*` PR; взять первую тему `draft`; прочитать только материалы из `basis` темы; написать по правилам тона; обновить план; `pnpm content:build`, `pnpm typecheck`, `pnpm test`; самопроверка; PR; ждать зелёных проверок; мерж.
- Расписание: облачная рутина, вторник и пятница (настраивается после первой ручной статьи).
- Первая статья пишется при владелице, проверяем весь путь до сайта.

## Отдельная задача (отдельный PR по «да» владелицы)

Самые крупные запросы закрываются заголовками и описаниями существующих страниц, а не статьями: «рассчитать матрицу судьбы по дате рождения» (6 274) — `/matrica-sudby`; «совместимость по дате рождения» (164 094) и «матрица совместимости по дате рождения» (3 624) — `/sovmestimost`; «22 аркан в матрице судьбы» (1 783) — страница аркана 22. Сначала смотрим текущие `title`/`description`/`h1`, затем предлагаем правки. Это код сайта, поэтому только по «да».

## Порядок работ

1. Спецификация → план реализации.
2. Работа в отдельной копии `C:\dev\oracle-articles` (ветка `feat/seo-articles`), основная папка не трогается.
3. PR «раздел статей» (код, тесты, план, `ci.yml`, IndexNow). Мерж по «да».
4. `docs/oracle-article-writer.md`.
5. Первая статья при владелице.
6. Расписание (вторник и пятница).
7. Отдельный PR с заголовками страниц.
