## 1. Решения

| Вопрос | Решение |
|---|---|
| Что продаём | **Разбор всей матрицы по темам** за 390 ₽: семь глав (§2). Ввод — только дата, без вопроса пользователя. Глава «Ваш вопрос» — возможное дополнение позже. |
| Из чего пишет ИИ | ИИ — редактор готовых блоков, а не автор (подход Граней). В каждый аркан добавляются две секции: «В отношениях» и «В деньгах и деле» (44 блока, вычитка владелицы). Род и предназначения — из «Сути» аркана и описания позиции. Секции «В роду» и «Как предназначение» — позже, если Wordstat покажет спрос. |
| Вход | Покупка только после входа через VK ID. Гость идёт на вход через `next`, как в «Войти и сохранить». |
| Привязка | Разбор привязан к **дате на момент покупки** (снимок в покупке). Смена даты в портрете старый разбор не трогает; новая дата — новая покупка. Одна и та же дата второй раз не продаётся. Покупок «для другого человека» нет. |
| После оплаты | Экран ожидания на странице разбора, без уведомлений в VK. Если ИИ не справился — глава собирается из блоков без ИИ. |
| Возвраты | Полный возврат до показа разбора и при технических сбоях — по письму на почту владелицы, вручную в кабинете ЮKassa. После показа разбора услуга оказана. Разбор после возврата не скрывается. |
| Чеки | Владелица оформляет чеки в «Мой налог» **вручную**. Сайт просит обязательный «E-mail для чека» и передаёт его в описании платежа ЮKassa. |
| Шеринг | Разбор личный, `noindex`, ссылкой не делится. Публичная карточка для шеринга — после рекламного теста. |
| Техническая схема | Как в Гранях: очередь `pg-boss` в той же Postgres, отдельный контейнер `apps/worker`, `packages/ai` с GigaChat. |

## 3. Экраны

### Блок продажи на `/matrica-sudby`

Один платный блок под бесплатным результатом, перед связкой «Скоро — Лила». Показывается только при включённом `PAID_REPORTS` (§8).

- Заголовок «Разбор всей матрицы — 390 ₽».
- Оглавление семи глав с арканами этого человека («Отношения — 6 Влюблённые · 17 Звезда»). Считается в браузере из уже рассчитанной матрицы, без ИИ и без сервера.
- Короткий статичный образец: один абзац того, как читается глава (на примере, одинаковый для всех).
- «Готов за несколько минут, хранится в „Моём портрете“».
- Кнопка по состоянию:
  - гость — «Войти и купить разбор» → `/login?next=/matrica-sudby`;
  - вошедший — поле «E-mail для чека» (обязательное, проверка формата) и кнопка «Купить разбор — 390 ₽». Если даты нет в портрете или она другая, страница сначала сохраняет дату через `/api/profile/birth-date` (правила 2а §5: портрет без спроса не перезаписывается — при другой дате в портрете блок продаёт разбор даты из портрета);
  - разбор этой даты уже куплен — «Открыть разбор».
- Ошибка создания платежа — сообщение в `role="alert"` и та же кнопка.

### Страница разбора `/portret/razbor/[id]`

`id` — id покупки. Видит только владелец покупки (чужой или несуществующий id — 404). `noindex`, в `robots.txt` уже закрыт `/portret/*`. Сюда же ведёт `return_url` ЮKassa.

Состояния:
1. **Ждём подтверждения оплаты** — страница раз в 3 секунды спрашивает статус; сервер при этом сверяет платёж с API ЮKassa (§4).
2. **Готовим разбор** — «обычно до 5 минут», что происходит; опрос продолжается.
3. **Оплата не прошла** — кнопка «Попробовать снова» (новая попытка покупки той же даты).
4. **Готовый разбор:**
   - обложка: иллюстрация аркана центра (`arcanumImage`, 960 px), «Разбор матрицы судьбы», дата «по дате 18.11.1988», оглавление со ссылками на главы;
   - семь глав; у глав 1–6 в заголовке номера и названия арканов со ссылками на их страницы;
   - дисклеймер (`DISCLAIMER`).

Текст глав выводится как обычный текст по абзацам; HTML из ответа модели не выводится.

### «Мой портрет»

Карточка «Разборы»: список купленных разборов — дата, по которой куплен, и ссылка «Открыть разбор». Без покупок карточки нет.

### Тексты — дословно (добавить в AGENTS.md)

«Разбор всей матрицы — 390 ₽», «Войти и купить разбор», «Купить разбор — 390 ₽», «Открыть разбор», «Попробовать снова», поле «E-mail для чека», в подвале ссылка «Оферта». На странице разбора ровно один `<h1>`; статусы ожидания — `role="status"`, ошибки — `role="alert"`.

### Для Codex

Визуал рисует владелица в Codex: блок продажи, экран ожидания (оба состояния и ошибка), страница готового разбора с обложкой, карточка «Разборы» в портрете. Сначала — каркас (`docs/design/wireframes/matrix-paid.html`) и бриф, затем встраивание и проверка (375 px, контраст AA, фокус, `prefers-reduced-motion`).

## 4. Данные и оплата

### Таблицы (`packages/db`)

`purchases`:
- `id` uuid, `user_id` → `users` (пользователь не удаляется физически, поэтому ссылка всегда жива);
- `product` enum, пока одно значение `matrix_report`;
- `birth_date` date, nullable — снимок даты; обнуляется при удалении данных;
- `receipt_email` text, nullable — обнуляется при удалении данных;
- `amount_kopecks` integer (39 000);
- `status` enum `pending | succeeded | canceled`;
- `yookassa_payment_id` text unique, `confirmation_url` text;
- `created_at`, `paid_at`.
- Индекс по `(user_id, created_at)`.

`reports`:
- `id` uuid, `purchase_id` → `purchases`, unique, `on delete cascade`;
- `chapters` jsonb — семь глав, у каждой `source: "ai" | "fallback"`;
- `created_at`.

Цена — константа в `packages/core` (`MATRIX_REPORT_PRICE_KOPECKS = 39_000`), в одном месте для блока продажи, оферты и платежа.

### Покупка

1. `POST /api/purchases` `{ email }`. Проверки: вход; дата в портрете; e-mail по формату; разбора этой даты ещё нет (есть `succeeded`-покупка той же даты → ответ со ссылкой на неё); частота запросов (`rate-limit`). Неоплаченная покупка той же даты моложе 30 минут → отдаётся её `confirmation_url`, новый платёж не создаётся.
2. Создание платежа в ЮKassa: 390.00 RUB, `capture: true`, описание «Разбор матрицы судьбы — «Твой оракул», чек: <e-mail>» (≤ 128 знаков; при длинном адресе — «чек: см. метаданные»), `metadata.purchaseId`, `metadata.receiptEmail`, ключ идемпотентности = id покупки, `return_url` = страница разбора. Ошибка шлюза → покупка `canceled`, пользователю — общее сообщение.
3. **Статус меняется только сверкой с API ЮKassa** (`GET /payments/{id}`): совпадают `metadata.purchaseId` и сумма; `succeeded` + `paid` → `succeeded`, `paid_at`, постановка задачи генерации; `canceled` → `canceled`. Сверку запускают:
   - `POST /api/yookassa/notification` — принимается только с IP-адресов ЮKassa, тело не используется кроме id платежа; ответ 200 без подробностей;
   - запрос статуса со страницы разбора, если покупка ещё `pending`.
4. Оплачено, а разбора нет — задача ставится ещё раз с тем же id (`pg-boss` не создаст дубль).
5. Двойная оплата одной даты (две вкладки): вторая покупка тоже `succeeded`, но генерация не запускается; её страница ведёт на первый разбор; в лог — `warn` «duplicate paid purchase — refund manually» с id покупки.

### Удаление данных

`deleteUserData` дополнительно: удаляет `reports` пользователя, в `purchases` обнуляет `birth_date` и `receipt_email`. Сумма, статус, `paid_at` и id платежа остаются для налогового учёта. Браузерные копии — как в 2а.

### Секреты

`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `GIGACHAT_AUTH_KEY` — только в `/opt/oracle/.env` на сервере (и в локальном `.env.development.local` владелицы для тестового магазина). В чат, репозиторий и логи не попадают. Переменные проверяются при старте (`env.ts`), в `deploy/env.example` — только имена.

## 5. Генерация

### Контент (`packages/content`)

- В каждый `arcana/NN-slug.md` — секции «В отношениях» и «В деньгах и деле» (2 абзаца, язык гипотез, «вы», нейтральный род). Проверка сборки: секции обязательны, стоп-список действует. Страницы арканов выводят новые секции (на телефоне — в `<details>`, как остальные).
- Новый `positions.md` — семь описаний глав: что значит позиция в матрице (2–3 предложения). Вход для ИИ и вступление глав в запасном варианте.
- Черновики пишет Claude, вычитывает владелица до выкладки (как в 2а).

### `packages/ai`

- Провайдер GigaChat (перенос из Граней): OAuth-токен по `GIGACHAT_AUTH_KEY`, модель — переменная окружения, таймаут, сертификат Минцифры через `NODE_EXTRA_CA_CERTS`.
- `buildChapterInput(matrix, content, chapter)` — только номера и названия арканов и тексты блоков. Имени, даты, id пользователя и покупки во входе нет (проверяется тестом).
- Промпт: правила ORACLE — связать блоки в цельный текст, не добавлять фактов, язык гипотез, «вы», нейтральный род, без предсказаний, диагнозов, запугивания, ответ — только JSON по схеме главы.
- Проверка ответа: схема, длина (§2), стоп-список из `packages/content`. Не прошёл — повтор, до 3 попыток на главу.
- Запасной вариант `fallbackChapter`: вступление из `positions.md` + блоки арканов главы; для главы 7 — ресурс, перекос, действие и вопрос аркана центра.

### `apps/worker`

- `pg-boss`, очередь `generate-report`, задача `{ purchaseId }`.
- Разбор уже есть → выход. Покупка не `succeeded` или дата обнулена → выход с записью в лог.
- Главы 1–6 параллельно, глава 7 — после них (на вход — первые абзацы глав 1–6). Нет ключа GigaChat → все главы запасные.
- Сохранение разбора; вторая запись для той же покупки невозможна (unique).
- Логи — без текста глав и без ответов провайдера; ошибки провайдера пользователю не показываются.
- Контейнер: `mem_limit: 250m`, `stop_grace_period: 30s`, том `./certs:/certs:ro`; образ собирается и выкладывается тем же `deploy.yml`.

## 6. Документы

- **`/oferta`** (новая, индексируется, ссылка «Оферта» в подвале): исполнитель — самозанятая (`OPERATOR`: ФИО, ИНН, почта); услуга и цена из константы; акцепт — оплата; порядок оказания (после оплаты, несколько минут, в «Моём портрете»); чек «Мой налог» на указанный e-mail; возвраты (§1); какие данные уходят сервису подготовки текста; 18+; дисклеймер.
- **`/contacts`**: кто оказывает услугу, что продаётся и по какой цене, как получить услугу, ссылка на оферту, почта. Телефон — по решению владелицы.
- **Политика — новая редакция** (версия и дата — в день PR): получатели ЮKassa (сумма, назначение платежа, e-mail для чека; данные карты вводятся на стороне ЮKassa) и сервис подготовки текста GigaChat (ПАО Сбербанк; номера арканов и тексты блоков, без имени и даты); цель «приём оплаты»; что остаётся после удаления данных.
- **Согласие при входе не меняется**: новые получатели работают по договору (оферте). `LOGIN_CONSENT_RECIPIENTS` фильтрует их явно, тест проверяет, что текст согласия прежний.
- **Владелице проверить:** есть ли «адрес электронной почты» в категориях данных уведомления РКН от 27.09; если нет — информационное письмо об изменении сведений.

## 7. Аналитика и ошибки

- Цели Метрики (после согласия на cookie): `report_offer_click` (кнопка в блоке продажи), `report_paid` (страница разбора впервые увидела `succeeded`), `report_opened` (показан готовый разбор).
- Сбой создания платежа, ошибка сверки, недоступный GigaChat — пользователь видит понятное сообщение или запасной разбор; подробности — только в логах сервера.

## 8. Запуск

1. Локально — тестовый магазин ЮKassa (ключи владелица кладёт в свой `.env.development.local`).
2. Выкладка с `PAID_REPORTS=off`: блока продажи нет, `/api/purchases` отвечает 404; новые секции арканов, оферта и контакты уже на сайте. ЮKassa модерирует сайт по оферте и контактам.
3. Владелица: боевые ключи ЮKassa и GigaChat в `.env`, адрес уведомлений `https://tvoy-orakul.ru/api/yookassa/notification` (события `payment.succeeded`, `payment.canceled`), `PAID_REPORTS=on`, перезапуск.
4. Одна настоящая покупка → разбор от ИИ → e-mail в описании платежа → чек вручную → возврат через кабинет.

Пошаговые инструкции для кабинетов и сервера готовит Claude; действия выполняет владелица.

## 9. Тесты

- `packages/db` (PGlite): покупки, разборы, удаление данных (разборы удалены, дата и e-mail обнулены, запись об оплате цела).
- Сервис покупок с подменённым шлюзом: сверка суммы и `purchaseId`, повторное использование `pending`, уже купленная дата, двойная оплата, ошибка шлюза, IP уведомлений.
- `packages/ai`: вход без имени и даты, промпт, проверка ответа (схема, длина, стоп-список), повторы, запасной вариант для всех семи глав.
- `packages/content`: 22 × 2 новые секции, `positions.md` — семь описаний.
- e2e: гость видит блок → «Войти и купить разбор» → вход (`/api/dev/login`) → «Купить разбор — 390 ₽» → локальный тестовый маршрут оплаты вместо ЮKassa (только при `DEV_LOGIN=1`) → ожидание → разбор из запасных блоков (ключа GigaChat в e2e нет) → карточка «Разборы» в портрете → «Удалить мои данные» → страница разбора 404. При `PAID_REPORTS=off` блока нет.
- Покрытие `packages/*/src`, `apps/web/src/server`, `apps/web/src/lib`, `apps/worker/src` ≥ 80 %.
- Полное ревью (исполнитель + ревьюер) — только задачи оплаты, данных и безопасности; остальное — самопроверка.

## 10. Не входит в 2б

Сообщения в VK о готовности; публичная карточка для шеринга; глава «Ваш вопрос»; секции «В роду» и «Как предназначение»; промокоды и скидки; автоматические возвраты и чеки; покупка разбора на чужую дату.

2б выложен на tvoy-orakul.ru, `PAID_REPORTS=on`, реальная покупка прошла и возвращена, 44 новых блока и `positions.md` вычитаны владелицей, e2e зелёные.
