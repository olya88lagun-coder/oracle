# Цели Яндекс.Метрики

Счётчик 113068094. Цели отправляются из браузера (`reachGoal`), только тем посетителям, кто нажал «Принять» в баннере cookie; тем, кто выбрал «Только необходимые», ничего не уходит. Поэтому цифры в Метрике — по согласившимся, а не по всем. Параметров у целей нет, кроме двух закрытых списков: `kind=lila` у PDF Лилы и `product` (`matrix`, `compat`, `lila`, `natal`) с необязательным `error` (код из известного списка или `unknown`) у `checkout_redirect` и `checkout_error`. Ни дат, ни намерений, ни почты, ни номеров покупок. Список целей в коде — `apps/web/src/lib/analytics.ts` (`GOALS`), срабатывание проверяют `e2e/goals.spec.ts` и `e2e/purchase-analytics.spec.ts`.

Старые цели и настройки счётчика сохранены. Для нового события: Метрика → «Цели» → «Добавить цель» → тип «JavaScript-событие» → точный идентификатор.

## Воронки (составные цели Метрики, до 5 шагов)

1. **Разбор матрицы:** `matrix_calculated` → `report_offer_view` → `report_offer_click` → `report_paid` → `report_opened`.
2. **Разбор из совместимости:** `compat_calculated` → `compat_offer_view` → `compat_offer_click` → `report_paid` → `report_opened`. `report_paid` общая для обоих входов, различаются началом цепочки.
3. **Лила с проводником:** `lila_offer_view` → `lila_offer_click` → `checkout_redirect` → `lila_paid`. Бесплатная партия — отдельная цепочка `lila_start` → `lila_finish`: начало обычной партии не шаг покупки проводника, поэтому в составную цель продажи его не включать. Гость, который идёт ко входу, виден по `lila_login_click`; после входа он возвращается на тот же экран и проходит цепочку заново (вход и оплата проходят на чужих страницах). Старт платной партии отдельной целью не отмечается: продажа считается по подтверждённой оплате, а не по запуску игры.
4. **Натальная карта:** `natal_to_calculator` → `natal_calculated` → `natal_save_click`. Страницы значений открыты по партиям: первый шаг считает только переходы с принятых страниц.
5. **Разбор натальной карты:** `natal_calculated` → `natal_offer_view` → `natal_offer_click` → `checkout_redirect` → `natal_paid` → `natal_report_opened` (в `checkout_*` параметр `product=natal`).
6. **Возвращаемость:** `taro_draw` и повторные визиты (отчёт «Повторные визиты» или сегмент по целям).

## Учёт покупок и суммы

Ecommerce уже включён в кабинете Метрики. Приложение инициализирует счётчик с `ecommerce: "dataLayer"`. Формат отправки соответствует [документации Яндекса](https://yandex.ru/support/metrica/ru/ecommerce/data).

`PurchaseAnalytics` работает во всём приложении. Он ждёт согласия и выполнения SDK-вызова [getClientID](https://yandex.ru/support/metrica/ru/objects/get-client-id); значение ClientID не сохраняется и не передаётся приложению. Наличие временной функции-очереди `ym` готовностью SDK не считается. До согласия нет ни загрузки SDK, ни запроса покупок. После позднего согласия, перехода по сайту, возврата фокуса или восстановления сети запрос можно повторить. Ожидающие открытия отчёта (`report_opened`, `natal_report_opened`) срабатывают, только пока этот отчёт открыт. Прошлые клики не воспроизводятся.

`POST /api/analytics/purchases` проверяет origin и сессию. Пользователь и покупки из тела запроса не принимаются. `claimPurchaseAnalytics` в транзакции выбирает только свои `succeeded` с положительной суммой, `paid_at` и ID платежа ЮKassa. Таблица `purchase_analytics` с уникальным `purchase_id` разрешает отправку одной покупки только одному запросу, в том числе из разных браузеров. Бесплатный доступ владелицы, отменённые и ожидающие платежи не считаются продажами. Миграция 0008 отмечает все существующие успешные покупки как исторические: открытие старых отчётов после выкладки не создаёт новые продажи. Старые ожидающие платежи, подтверждённые после миграции, могут учитываться.

Браузер отправляет `report_paid`, `natal_paid` или `lila_paid` без параметров и ecommerce-покупку: отдельный случайный `transaction_id`, статические код/название продукта, фактическая сумма из покупки в рублях (`amount_kopecks / 100`), валюта `RUB`, количество 1. Реальные UUID покупки/пользователя, почта, данные рождения, город и намерение не отправляются. Учёт проверяет готовность также после ответа сервера, поэтому отзыв согласия подавляет отправку.

Серверный claim означает однократное **разрешение** на отправку, а не подтверждение доставки в Яндекс. Если вкладка закрылась, согласие отозвано или сеть/блокировщик остановили запрос после claim, событие может потеряться. Метрика не заменяет реестр платежей и не показывает все продажи без согласия. Сверять выручку нужно с подтверждёнными платежами и базой. Локальные HTTPS-тесты используют поддельную оплату и перехватывают SDK/запросы Яндекса; это не доказательство внешней доставки.

В аргументах наших `hit` и внутренних `referer` UUID-сегменты личных адресов заменяются на `:id`; например, `/portret/razbor/:id`. Это не меняет настоящие маршруты и сохраняет общую статистику раздела. Отдельно нужно учитывать автоматические запросы SDK: эта очистка не является доказательством содержания всех запросов стороннего скрипта.

`checkout_redirect` перед уходом на оплату ждёт отправки цели не дольше 300 мс. Вход через VK ID и оплата на странице ЮKassa проходят на чужих страницах, цели между ними не ставятся. Webvisor остаётся выключен в инициализации приложения. Ограничение доменом и исключение собственных визитов в кабинете не меняются.

## Проверка перед выкладкой

`pnpm typecheck` и `pnpm test:coverage` проверяют код, API, миграцию и claim. DB-тесты используют PGlite: уникальный ключ и транзакция защищают от гонок, но эти тесты не моделируют отдельные сессии полноценного PostgreSQL.

Для `e2e/purchase-analytics.spec.ts` нужны отдельная локальная БД, воркер и `next dev` с локальным HTTPS-сертификатом. `APP_URL`, `NEXT_PUBLIC_SITE_URL` и `E2E_BASE_URL` должны совпадать, например `https://localhost:3000`. Использовать `DEV_LOGIN=1`, `PAYMENTS=fake`, `PAID_REPORTS=on`, `PAID_LILA=on`, `PAID_NATAL=on`, `OWNER_VK_ID=dev-Владелица`; другие имена владельца задаются через `E2E_OWNER_NAME`. Сертификаты, ключи и тестовую базу не коммитить. На HTTP этот набор пропускается, чтобы не ослаблять проверку домена/HTTPS ради тестов.

```powershell
$env:E2E_BASE_URL = 'https://localhost:3000'
pnpm exec playwright test -c e2e/playwright.config.ts e2e/purchase-analytics.spec.ts e2e/goals.spec.ts --workers=1
```

Сценарии проверяют отсутствие SDK/claim до согласия и готовности; согласие позже 10 секунд; сумму каждого продукта; открытие готового отчёта после согласия; повтор, перезагрузку и новый браузер без localStorage; исключение бесплатного доступа владелицы. Транспорт Яндекса перехватывается, настоящие продажи не создаются.

После owner merge: подтвердить применение миграции 0008 и успешную выкладку; проверить загрузку SDK после согласия и события в отладчике Метрики. При проверке настоящей оплаты отдельно сверить сумму и статус в платёжном реестре. До этого внешняя доставка нового ecommerce-кода не считается подтверждённой.
